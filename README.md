# kytyps5-nightly-bin

AUR packaging for the prebuilt Linux nightly releases of
[KytyPS5](https://github.com/KytyPS5/KytyPS5), a PlayStation 5 emulator.

Upstream publishes a dated release (e.g. `KytyPS5-2026-08-15-566a450`) with a
`-Linux-x86_64.tar.gz` asset; this package tracks that asset. Nothing is
compiled — the archive already bundles its own Qt 6 runtime.

## Building

```sh
makepkg -si
```

Then run `kytyps5`, or start **KytyPS5** from the desktop menu.

## Nightly updates

`.gitlab-ci.yml` bumps the package to the newest upstream release and pushes the
commit to both the AUR and this GitLab repo. It needs:

| CI/CD variable | Type | What |
| --- | --- | --- |
| `AUR_SSH_KEY` | File, protected | Private key of an SSH key registered on the AUR account owning this package |
| `GITLAB_PUSH_TOKEN` | Variable | Project access token with `write_repository` |

Then add a **daily** schedule under *Build > Pipeline schedules*. The job only
runs from a schedule or a manual *Run pipeline*, never on push.

The asset is never downloaded. `source=` points at the permanent
`releases/download/<tag>/<asset>` URL, and the checksum comes from the digest
GitHub publishes with the release; if that digest is missing the job fails
rather than guess. Nothing is built before publishing either, so a broken
upstream nightly reaches the AUR unverified — a deliberate trade, but worth
knowing when a bug report arrives.

It tracks the newest release *that has a Linux tarball* rather than
`/releases/latest`, because upstream's Linux build fails often enough that the
newest release regularly ships Windows and macOS assets only (2 of the last 10
at the time of writing).

The AUR branch is `master`, so the pipeline pushes `HEAD:master` there and
`HEAD:$CI_DEFAULT_BRANCH` here.

## Layout and why `/usr/bin/kytyps5` is a script

The payload is installed read-only under `/opt/kytyps5`, and `/usr/bin/kytyps5`
is a wrapper generated by `package()` rather than a symlink.

The upstream launcher is not relocatable: before starting a game it writes a
`kyty_run.sh` next to its own executable and runs the emulator with that
directory as the working directory, which is also where logs and `_SaveData`
end up. Started straight from `/opt` it aborts with
`Can't create file: /opt/kytyps5/kyty_run.sh`, and there is no fallback path —
it calls `QApplication::quit()`.

So the wrapper — seven lines, generated by `package()` — assembles a writable
per-user application directory at `~/.local/share/kytyps5`: the emulator,
`lib/`, `plugins/` and `qt.conf` are symlinked in from `/opt`, while `launcher`
is copied. The copy is not optional — Qt resolves `applicationDirPath()`
through `/proc/self/exe`, which follows symlinks, so a symlinked launcher would
resolve back to `/opt` and defeat the whole arrangement. `cp
--remove-destination` refreshes it on every launch without tripping over an
already running instance.

Launcher settings live in `~/.config/Kyty/Kyty.ini`, per upstream's own Linux
code path.

## Notes

- Requires a Vulkan 1.3 capable GPU and driver.
- The launcher opens the emulator in a terminal emulator when it finds one
  (`$TERMINAL`, `konsole`, `alacritty`, `kitty`, `foot`, `xterm`, …), and falls
  back to running it without a terminal otherwise. Hence the `optdepends`.
- Two duplicate copies of each bundled library ship in the archive (SONAME and
  fully versioned); `package()` collapses the SONAME copy to a symlink, saving
  about 68 MiB installed.
- The archive also carries build leftovers (xbyak/Zydis headers, `libZydis.a`,
  CMake package files) that are not installed.
- `makepkg` refuses to run as root and checks that *before* it handles
  `--printsrcinfo`, which is why the pipeline regenerates `.SRCINFO` as a
  non-root `builder` user.
